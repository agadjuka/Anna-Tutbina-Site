### Технические заметки для новой сессии

- **Запись в Sanity без диалога с заказчиком** — рабочий приём этой сессии:
  `cd sanity && ASSET_DIR=<путь> npx sanity exec <script>.cjs --with-user-token`.
  CLI уже авторизован локально (администратор проекта), скрипт получает клиент
  через `require('sanity/cli').getCliClient()` — **обязательно `.cjs`, не `.mjs`**
  (ESM-импорт `sanity/cli` в `sanity exec` ломается с "does not provide an export
  named 'getCliClient'", в CJS всё нормально). Скрипт держать временно и удалять
  после — не коммитить в `sanity/`.
- **Скриншоты** — Browser pane в этой машине не рендерит кадр
  (`computer{screenshot}` падает с "pane is not displayed"). Рабочая замена —
  отдельный Playwright в scratchpad-папке, см. память `reference-playwright-screenshot-tool`.

## Что мы делаем

Заказчик прислал готовый дизайн главной страницы в Figma. Задача — **заменить текущую
главную на этот дизайн**, разбирая его по блокам.

**Источник дизайна:**
`https://www.figma.com/design/1FMa8mpXz5izCNZ9kAwpnx/Untitled?node-id=0-1`

- `fileKey` = `1FMa8mpXz5izCNZ9kAwpnx`
- Лист `Page 1` = нода `0:1`
- Корневой фрейм страницы = `5:2` (1920 × 9551)

Доступ к Figma — через **remote MCP-сервер** (`https://mcp.figma.com/mcp`, HTTP, OAuth).
Локальное расширение `ant.dir.ant.figma.figma` (инструменты `mcp__Figma__*`) требует
запущенного десктопного Figma и **не используется** — брать remote-инструменты.

Полезные вызовы:
```
get_metadata(fileKey, nodeId)      — структура поддерева
get_screenshot(fileKey, nodeId)    — PNG (отдаёт короткоживущий URL, качать curl'ом)
get_design_context(fileKey, nodeId)— код + вычисленные значения цветов/размеров + ассеты
```

⚠️ `get_variable_defs` на этом файле возвращает `{}` — **переменных Figma в файле нет**.
Автоматического маппинга «переменная → токен» не будет, значения снимать через
`get_design_context` и вручную сопоставлять с токенами проекта.

⚠️ Файл — импорт с существующего сайта (плагин типа html.to.design): имена слоёв вида
`Slot → Summary`, `Paragraph+Background`, картинки `IMG_0744 1`, автолэйаутов почти нет,
координаты абсолютные. **Макет — референс по внешнему виду, а не по структуре разметки.**
Верстаем по-своему: адаптивно, на Tailwind, с нормальной семантикой.

## Жёсткие правила

### 1. Шрифты не меняем

Из дизайна берём **только композицию, цвета, размеры, отступы**. Шрифты остаются проектные,
из [`lib/fonts.ts`](../../lib/fonts.ts):

| Роль | Шрифт | Как применять |
|---|---|---|
| Заголовки | Cormorant | `font-heading` (и так по умолчанию на `h1`–`h6`) |
| Основной текст | Kinetika | по умолчанию на `body` |
| Логотип | LaLuxes | `font-logo` |
| Подзаголовок логотипа | MADE TheArtist Script | `font-logo-subtitle` |

`lib/fonts.ts` — **генерируемый файл**, руками не править.

### 2. Бэкенд не переделываем

Главный принцип задачи: **дизайн — это только отображение**. Всё, что уже приходит из Sanity,
переиспользуем как есть, новые схемы заводим только там, где контента реально нет.

Уже готово и должно быть переиспользовано без изменений:

| Данные | Тип Sanity | Запрос в `lib/sanity.queries.ts` | Готовые хелперы |
|---|---|---|---|
| Туры (карточки) | `tour` | `toursQuery` | `isTourVisibleOnSite()` |
| Отзывы | `tour.reviews[]` | `toursWithReviewsQuery` | `flattenReviewsFromTours()` |
| Индивидуальный тур | `customTour` | `customTourQuery` | — |
| FAQ | `faq` | `faqQuery` | — |
| Заголовки блоков главной | `homePage` (синглтон) | `homePageQuery` | — |
| Футер и контакты | `siteSettings` (синглтон) | `siteSettingsQuery` | — |

⚠️ Тип `about` («Обо мне») **удалён** — такого раздела нет в макете. Не путать со схожим
по названию новым блоком «О проекте» (`homePage.about`) — это другая сущность.
Подробности и история решения — [`sanity-plan.md`](sanity-plan.md), [`legacy.md`](legacy.md).

Схема `homePage` **заведена сразу вся** (все 9 секций), не по одному блоку — решение
заказчика от 2026-08-11. Дальше по блокам меняется только вёрстка, в схему лезть
не нужно, кроме случаев, когда всплывёт что-то незапланированное.

Новое заводим по правилу проекта — **3 правки**: схема в `sanity/schemas/` → запрос в
`lib/sanity.queries.ts` → рендер в компоненте. Инлайновых GROQ в компонентах не делаем.

### 3. Все картинки — из Sanity

Никаких файлов из макета в `public/`. Каждое фото в новых блоках — поле в Sanity,
рендер через `<SanityImage>` из [`components/ui/sanity-image.tsx`](../../components/ui/sanity-image.tsx).
Под это заведён документ-синглтон `homePage` — см. [`sanity-plan.md`](sanity-plan.md).

### 4. Цвета — только токены

Палитра дизайна предварительно **совпадает** с существующей в
[`app/globals.css`](../../app/globals.css): фон `#EEEAE4` = `--color-background`,
оливковая кнопка ≈ `#69695C` = `--color-primary`, текст `#1E1E1C` = `--color-foreground`.
Сверять на каждом блоке через `get_design_context`. Хардкод hex — запрещён;
если в дизайне встретился цвет вне палитры — не хардкодить, а завести токен в `@theme`
и **отметить это в отчёте заказчику**.

### 5. Серверные компоненты по умолчанию

`"use client"` — только там, где нужны хуки/DOM: карусели, аккордеоны, анимации на
IntersectionObserver, переключатели. Данные грузим в `app/page.tsx` (серверный) и
прокидываем пропсами.

### 6. После КАЖДОГО блока — явный чек-лист действий в Sanity

**Это правило появилось после реального провала 2026-08-11:** блок HERO был готов
в коде, но заказчик потратил ~50 минут, пытаясь понять, почему на сайте пусто.
Причина — данные лежат в Sanity, а документ `homePage` не был создан и опубликован.
Это было сказано в отчёте, но **одной строкой в середине текста** — потерялось.

Начиная с этого момента, если блок зависит от данных в Sanity, отчёт по блоку
**обязан** открываться отдельным, визуально выделенным разделом — раньше описания
того, что сделано в коде:

```
## ⚠️ ЧТОБЫ УВИДЕТЬ РЕЗУЛЬТАТ, СНАЧАЛА СДЕЛАЙ В STUDIO:
1. Открыть <ссылка на Studio>
2. Открыть документ «...»
3. Заполнить поля: ... (перечислить конкретно, что обязательно, а что нет)
4. Нажать Publish
```

Если блок ничего не требует от заказчика (например, только код или уже
опубликованные данные) — так и написать явно: «Действий в Sanity не требуется,
можно смотреть сразу».

**Также по умолчанию держать Studio задеплоенной.** Хостинг-URL Studio
(`npm run sanity:deploy`) — это единственное место, где заказчик реально правит
контент; локальная `npm run sanity:dev` ему не нужна. После **любого** изменения
схемы (`sanity/schemas/*`, `sanity/structure.js`) — сразу прогонять
`npm run sanity:deploy`, не дожидаясь, пока попросят. Деплой не разрушает данные
и не требует подтверждения — можно запускать сразу же после правки схемы.

### 7. Анимационной библиотеки в проекте нет

`framer-motion` не установлен. Анимации делаем на CSS (`@keyframes` в `globals.css` +
Tailwind-классы) и на `IntersectionObserver` для появления при скролле.
Ставить новую зависимость — **только с явного согласия заказчика**.
Обязательно уважать `prefers-reduced-motion`.

### 8. Мобильная версия — обязательна для каждого блока, не бонус после

**Правило появилось 2026-08-11**, после того как заказчик посмотрел мобильную HERO
и она не устроила (кнопки вертикальные и слишком тяжёлые, фото коллажа вообще не
показаны — `hidden` до `lg`). Причина — в Figma-макете мобильной версии нет
(см. `backlog.md`, п.4), и до этого момента мобильная раскладка молчаливо
доделывалась «как получится», без отдельного показа заказчику.

Начиная с этого момента, для **каждого** блока мобильная версия — часть сдачи блока,
не отложенная задача:

- Верстаем и её тоже, не только десктоп по Figma. Ориентиров из макета для неё нет —
  решения по композиции принимает агент, ориентируясь на десктопную версию блока
  (те же фото, тот же текст, тот же смысл раскладки), но не обязан копировать
  десктопную структуру пиксель-в-пиксель.
- В отчёте по блоку — **отдельный раздел с мобильной версией**: что сделано,
  скриншот/описание раскладки, чем она отличается от десктопной и почему.
- Заказчик утверждает мобильную версию блока отдельно от десктопной — «принято» по
  блоку означает принято и то, и другое. Если заказчик просит правки только по
  мобильной части — это не блокирует переход к следующему блоку по десктопу, но
  сам блок в `blocks.md` остаётся не-✅, пока не закрыты оба.
- Проверять на ширинах ≤767px (мобильный) отдельно от диапазона 1024–1919
  (планшет/ноутбук, см. баг из `backlog.md` п.1.5) — это разные раскладки.

## Рабочий процесс (согласован с заказчиком)

Работаем **по одному блоку за раз**, не пачками:

1. Агент снимает блок из Figma (`get_screenshot` + `get_design_context`).
2. Сверяет с [`blocks.md`](blocks.md): что за данные, что уже есть в Sanity, что новое.
3. Реализует **этот блок целиком — десктоп и мобильную версию** (см. правило 8:
   мобильная не Figma-референс, решения по композиции на усмотрение агента).
4. Прогоняет `npx tsc --noEmit`, смотрит через `/admin/` на десктопных и мобильных
   ширинах.
5. Даёт заказчику **краткий отчёт** с двумя разделами — десктоп и мобильная версия:
   что сделано, что взято из Sanity, что нужно заполнить в Studio, какие остались
   вопросы.
6. Заказчик проверяет обе версии → даёт добро → переходим к следующему блоку.
7. Агент отмечает статус блока в [`blocks.md`](blocks.md) и записывает туда новые
   комментарии заказчика (по десктопу и по мобильной — отдельно, если различаются).

**Не забегать вперёд.** Не начинать следующий блок, пока предыдущий не принят.
